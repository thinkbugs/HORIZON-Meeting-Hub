# 浏览器扩展投屏

HORIZON 自带一个 Chrome / Edge 扩展作为发送端：把**当前标签页**或**屏幕/窗口**的画面与声音编码后，通过局域网直连会议主机的 WebSocket 接收端。不经过云端、不需要登录、不依赖 Chromecast 设备。

扩展弹窗有三个分页：**投屏**（整屏/标签页镜像）、**文件**（多选文件落到主机接收目录）、**片库**（把视频/音乐/图片传进主机片库，并管理播放队列）。投屏只走 9407；文件与片库走 7878 的主机门户，与大屏、手机是同一份片库、同一条队列。

- 发送端：`extension/`（Manifest V3，Chrome/Edge 116+）
- 接收端：HORIZON 主程序内的浏览器投屏服务（`crates/horizon-cast`，端口 `9407`）
- 主机门户：文件传送页、片库 HTTP、媒体文件与媒体 API（`src-tauri/src/snapdrop_server.rs`，端口 `7878`）
- DLNA 渲染器：`crates/horizon-cast/src/dlna.rs`，端口 `8290`（扩展不用它）
- 播放端：主程序内的 WebCodecs 预览（`src/components/MirrorPreview.tsx`）、全屏观看界面（`src/components/CastStage.tsx`）与媒体舞台（`src/components/DlnaStage.tsx`）

## 安装扩展

1. 在 HORIZON 设置页打开「浏览器投屏」，点击**打开扩展目录**；安装版会定位到安装目录下的 `extension/`，开发版定位到源码目录。
2. 浏览器地址栏打开 `chrome://extensions`（Edge 为 `edge://extensions`），启用**开发者模式**。
3. 点击**加载已解压的扩展程序**，选择第 1 步打开的目录。
4. 可固定工具栏图标，之后点击图标即可投放。

扩展只需要四项权限，均为投放与发现必需：

| 权限 | 用途 |
| --- | --- |
| `tabCapture` | 抓取当前标签页画面与标签页声音 |
| `offscreen` | 在弹出的窗口关闭后继续持有采集、编码与 WebSocket 连接 |
| `storage` | 记住最近一次接收地址与发现结果 |
| `system.network` | 枚举本机网卡，只扫自己所在的 /24（否则一台三网卡的机器要扫三个网段） |

屏幕/系统音频采集通过 `getDisplayMedia` 在用户点击时授权，不申请常驻权限。访问局域网写在 `host_permissions: ["http://*/*"]` 里（`/info` 与 7878 都是明文 HTTP），不申请 `https://*/*`。

## 使用

1. 在 HORIZON 中开启浏览器投屏，面板会显示**接收地址**（形如 `ws://192.168.1.20:9407/stream?token=…`）。
2. 打开扩展弹窗：它会扫局域网并列出接收端（也可粘贴接收地址，自动补全 `ws://` 与 `/stream`，地址会记住）。
3. 选择投放方式：
   - **投放当前标签页**：抓取本标签页画面与声音，切换标签页不影响画面。
   - **投放屏幕或窗口**：系统选择器中选择屏幕、窗口或标签页，可勾选分享系统音频。
4. 投屏中弹窗显示画面尺寸、帧率、码率、时长与是否含声音；点击**停止投放**结束会话。

接收端同一时间只服务一路发送端，新连接会替换旧连接。扩展会自动重连，并在重连后请求新的关键帧。

### 分页：投屏 / 文件 / 片库

三个分页共用一次发现结果：选中（或手填）的接收端决定投屏地址，同一地址 `/info` 里的 `hub` 字段决定文件与片库的端口——扩展不写死 7878。

- **文件**：点投放卡选文件，或把文件拖进分页；可多选，`POST /upload` 一次性送到主机接收目录（默认 `Documents\meeting`），**不进片库、不影响投屏**。列表显示每行的类型标记、名称、大小与 `✕`，分组头汇总条数与总字节；整宽发送键在发送中禁用并显示不确定进度条（上传是单次请求，没有真实百分比），回执条区分成功与失败。重复选择或重复拖入按「名称 + 大小 + 修改时间」去重。
- **片库·队列**：显示当前队列（当前项、播放/暂停状态、时间）与主机片库。行内按钮：`▶` 只投这一条、`＋` 追加到队尾、`↑`/`↓` 调整顺序、`⇥` 预排为下一条、`✕` 从队列移除，点行即跳转；播放条发 `play`/`pause`/`stop`。排序用按钮而不是拖拽：372 px 的弹窗里拖拽既不可靠也没有键盘路径。
- **片库·本库**：`上传到片库`（多选，`POST /api/media/upload`）、`重新读取`、粘贴网络地址（`addUrl`，标为外链）、`✕` 删除。删除会连带把队列里的同一条移出。
- **轮询**：队列每秒读一次，只在片库分页可见时进行；片库列表不轮询，只在分页打开时读一次，之后由 `media-library` 事件（上传、改名、删除、addUrl）更新。原因见「主机接口」一节。

收到 `hub` 就说明主机片库服务在听；`/info` 里没有 `hub` 时扩展直接报「该接收端没有开启片库服务」，不会猜一个端口去撞别家的服务。

## 端口与服务

| 端口 | 服务 | 谁在用 |
| --- | --- | --- |
| `9407` | 浏览器投屏接收：`WS /stream?token=`、`GET /info` | 扩展投屏与扫频、安卓发送端 |
| `7878` | 主机门户：`/`、`/upload`、`/api/media/<action>`、`/api/media/upload`、`/media/<id>/<name>`、`/server/webrtc` | 扩展的文件/片库分页、大屏自己的媒体面板、安卓发送端 |
| `8290` | DLNA 媒体渲染器：`/dd.xml`、`/control/*`、`/evt/*` | 第三方 DLNA 控制器、手机系统投屏菜单 |

7878 与 8290 开机即绑，不依赖面板是否打开。7878 与 8290 的接口没有账号或令牌，局域网内可达即可用——和文件传送页同一信任模型；9407 的 `/stream` 要投屏码，`/info` 只要不投屏就不需要码。

## 主机接口（扩展实际使用的契约）

### `GET /info`（9407）

```json
{"service":"horizon-browser","name":"戎耀会","port":9407,"path":"/stream","paired":true,"hub":7878}
```

- `service` 必须是 `horizon-browser`，否则扫频不列出这台主机；
- `paired` 表示是否需要投屏码；`/info` 本身**从不含投屏码**；
- `hub` 是片库/文件服务的端口，由接收端从自己的 hub 基准地址里取出；片库服务没起来时**这个字段直接缺席**。老版本接收端的 `/info` 404，扩展仍把它当作可投屏的接收端，只是没有片库分页可用。

### 媒体 API（7878）

| 路由 | 方法 | 说明 |
| --- | --- | --- |
| `/` | GET | 文件传送页（扫码/局域网直传的旧入口） |
| `/upload` | POST | multipart，多文件，落**接收目录**；成功回纯文本 `成功保存 N 个文件` |
| `/api/media/upload` | POST | multipart，多文件，落**片库**；回 `{"items":[{id,title,kind,bytes,…}]}` |
| `/api/media/<action>` | GET / POST | 无参读取用 GET；改状态用 POST + JSON 体；错误回 `400 {"error":"…"}` |
| `/media/<id>/<name>` | GET / HEAD | 片库文件，支持 `Range` → `206`；`<name>` 只是给“按地址判类型”的播放器看的，查找只用 `id` |
| `/media/<id>` | GET / HEAD | 兼容旧地址（没有文件名尾巴），缓存过的控制器仍可用 |
| `/server/webrtc` | GET | 文件传送页的 WebRTC 信令 |

两个上传路由都是流式写盘，单文件上限 16 GiB；`/api/media/upload` 回 `OPTIONS` 预检，`/api/media/*` 的响应带 `Access-Control-Allow-Origin: *`，所以浏览器扩展、手机、DLNA 控制器可以来自不同来源。`/media/*` 是普通文件响应（带 `Range`/`Content-Range`），不额外加 CORS 头——播放元素与 DOM 缩略图不需要读正文。

`<action>` 与大屏 IPC 的动作名完全一致（`MediaStage::invoke` 是唯一 dispatcher）：

- 读：`library`、`queue`、`status`、`hasNext`
- 队列：`setQueue`、`enqueue`、`jump`、`next`、`previous`、`setNext`、`queueMove`、`queueRemove`、`clearQueue`、`order`、`repeat`、`dwell`
- 播放：`transport`（`play`/`pause`/`stop`/`seek`/`volume`/`mute`）
- 片库：`addUrl`、`rename`、`remove`

`jump`、`queueMove` 之类的位置参数接受 `index`（槽位，大屏按钮用）或 `id`（条目，手机与扩展用）。

### `local` 的判定

条目视图里的 `local` **不是按路径形状猜的**，而是「地址是否以本机 hub 的 `{base}/media/` 开头」：

- `http://192.168.0.27:7878/media/ab12/开场片.mp4` → `local=true`；
- `https://example.com/media/开场片.mp4` → `local=false`，扩展与大屏都标注「外链」——播放依赖发送端保持可达。

片库条目一律带 `local=true`；`addUrl` 进来的地址按上面的前缀判定。DLNA 控制器投回来的本机 hub 地址也会回查片库，所以标题与 `kind` 来自片库而不是地址尾巴。

### 队列同步：1 秒轮询，不是推送

`media-library` 事件只在**片库本身**变化时发（上传落库、`addUrl`、`rename`、`remove`）。手机、DLNA 控制器或另一个客户端改的是**队列**，这条事件不发——所以：

- 大屏舞台打开时每秒读一次 `queue`，只读队列，不读片库；
- 扩展片库分页打开时每秒读一次 `queue`，切回投屏分页立即停止；
- 片库列表靠 `media-library` 事件刷新，不轮询。

实测延迟：外部 `enqueue` 反映到大屏计数约 118 ms–1.0 s（贴着一秒轮询周期），上传落库反映到片库列表 53–58 ms（事件路径）。这是刻意的取舍：队列变化频繁且来源多，推送要维护订阅；列表变化低频，事件足够。

## 全屏观看

- 发送端开始投放时，接收端会自动接管整块屏幕：原生全屏、画面等比居中，浏览器投屏与 AirPlay 镜像共用同一套观看界面。
- 也可以在投屏面板中点击预览画面，或点击「全屏观看」手动进入。
- 顶部状态条显示来源、画面尺寸与发送端地址；点击「退出全屏」或按 `Esc` 返回启动器，并恢复进入前的窗口尺寸与全屏状态。
- 发送端断开时观看界面自动退出，不会停留在最后一帧。
- 观看期间启动器快捷键暂停响应，避免误启动后台应用。

## 画质与延迟

发送端固定实时编码策略，不追求最高码率，而是把端到端延迟压到最低：

- H.264（`avc1.640c1f`，High@3.1），`latencyMode: "realtime"`，最长边不超过 1920。
- 码率 `min(12 Mbps, max(1.5 Mbps, 宽×高×帧率×0.12))`；标签页文字内容使用 `contentHint: "detail"`。
- 关键帧每 5 秒一次；重连或解码器卡顿时由接收端显式请求，避免周期性大帧堆积。
- 发送队列深度为 1，宁可丢一帧也不排队，帧携带发送时刻时间戳用于端到端测量。
- 音频为 48 kHz 立体声 PCM s16le，与视频走同一条 TCP 连接。

在 Chrome 156、Windows 11、30 fps 真实屏幕采集下实测（同机回环，画面上叠加时间码）：

| 指标 | p50 | p90 | p95 |
| --- | --- | --- | --- |
| 玻璃到玻璃延迟（采集→显示） | 11.4 ms | 45.4 ms | 72.2 ms |
| 网络传输（编码输出→接收） | 9.7 ms | — | — |
| 主进程解码投递 | 1.6 ms | — | 3.5 ms |

队列积压 0、丢帧 0。局域网有线/优质 Wi-Fi 下应接近该水平；跨网段、代理或高负载无线环境会明显变差。

- 未在 macOS/Linux 浏览器、Safari、Firefox 上验证；这些浏览器不支持所需的 `tabCapture` / WebCodecs 组合。

### 已知限制

- 本机 GPU 的硬件 H.264 解码在 1080p30 出现 200–300 ms 级停顿；接收端检测到积压后会自动切换到软件解码，稳定后不再回切。软件解码在 1080p 有充足余量。
- 接收端为单路会话设计；多人同时投放会互相顶替。
- 首次使用必须手动加载解压扩展；如需免安装分发，可后续打包为商店扩展或企业策略强制安装。
- 7878 的文件与片库接口**没有鉴权**：同一局域网内任何设备都能上传、删除片库条目或改队列。这与「会议室里谁都看得见大屏」是同一信任模型，不适合暴露到不可信网络。
- 队列没有归属：手机、扩展、DLNA 控制器和大屏改的是同一条队列，谁的 `setQueue` 最后到谁说话。片库分页每秒轮询就是为了看见别人（例如手机）刚做的改动。
- 上传是单次请求，没有断点续传；中途断网需要重选文件。单文件上限 16 GiB。

## 协议摘要

- 传输：RFC 6455 WebSocket，`ws://<host>:9407/stream?token=<token>`，token 由接收端生成，错误 token 直接拒绝握手。
- 分帧：每帧 24 字节头 + 负载。
  - `kind` u8：`1` = H.264 Annex B，`2` = PCM s16le
  - `flags` u8：bit0 关键帧、bit1 时间戳为发送端墙钟、bit2 存在丢帧间隙
  - `pts_us` u64 LE：微秒时间戳
  - `width` / `height` u16：视频尺寸（音频为 0）
  - `payload_len` u32：负载长度
- 控制消息：发送端在文本帧发送 `{"type":"keyframe"}` 请求关键帧；接收端可在文本帧回发同一消息。
- 音频参数固定 48 kHz / 2 声道 / 16 bit，不额外协商。

## 故障排查

- **弹窗提示无法连接**：确认接收端已开启、地址与端口正确、两台设备在同一网段；防火墙需放行 TCP 9407。
- **片库分页提示「该接收端没有开启片库服务」**：接收端的 `/info` 里没有 `hub` 字段——通常是片库/文件服务（7878）没绑上，或防火墙没放行 7878。先在浏览器打开 `http://<大屏IP>:7878/api/media/library`，能回 JSON 才说明服务在听。
- **文件或片库操作超时**：`/api/media/*` 的读取预算 6 s，上传不设超时；大文件停留在「正在上传」是正常的，进度按已传字节显示，失败会给出主机自己的错误文案。
- **有画面无声音**：标签页本身可能静音；屏幕模式需在系统选择器中勾选「分享系统音频」。
- **画面卡住后自动恢复**：接收端检测到积压会重建解码器并请求关键帧；频繁发生通常是无线链路抖动或发送端 CPU 饱和。
- **扩展页 404 / 图标无响应**：重新在扩展管理页移除并加载一次目录；开发调试时改动 `offscreen.js` 后需在扩展页点击刷新。
- **Mac 找不到此 AirPlay 接收端**：Windows 防火墙可能阻止了入站 mDNS（UDP 5353）。请在「Windows 安全中心 → 防火墙和网络保护 → 允许应用通过防火墙」中确认 HORIZON 已勾选「专用」和「公用」网络，或手动添加规则放行 UDP 5353。
